# 全局预约协议与日历

本集成为每台割草机提供一个日历，用于管理全局**时间段**割草预约
（`SCHEDULE_TYPE_GLOBAL_V2`）。现有的预约总开关、七个按星期开关和下次预约传感器
继续保留。选区预约、沿边预约、旧版 `SCHEDULE_TYPE_GLOBAL`、频率预约及天气策略
不在该日历的范围内。GET 返回的其他预约类型会保留，日历操作不会修改它们。
频率模式下日历不可用，也不会自动切换模式。

## 固件能力

每次 MQTT 连接成功后，集成先订阅 `data_point/122/robot`，再直接发送 DP122 GET。
预约功能的可用性不依赖 DP127 或 `module.schedule`。只有读取到有效的时间段模式
预约列表后，日历才可用，空列表也有效。频率模式及格式损坏的数据不会启用日历。
日历每 300 秒（五分钟）轮询一次，首次 GET 失败后可通过轮询重试，无需重新连接。
连接后的读取、日历事件查询和写入验证 GET 均立即执行，不受该轮询间隔限制。

协议定义了以下固件能力，供参考；集成不会把上报的版本号作为功能启用条件：

| 预约模块版本 | 相关能力 |
| --- | --- |
| 0–1 | 旧版格式，不在该日历范围内 |
| 2 | GLOBAL_V2 每周预约、全局禁用、按星期禁用 |
| 3 | 增加 `basic_config.run_once` |
| 4+ | 增加 `repeat_until_end_time` |

有效 GET 只能确认状态可读，不能证明固件支持写入。每次写入都必须收到匹配的成功
ACK，并通过 GET 回读验证。新增每周预约时，未使用的可选字段（`run_once`、
`repeat_until_end_time`）会省略；编辑时保留已有的可选字段。请求非默认的可选值时
会发送相应字段，并要求回读确认；固件静默忽略这些值也会报告失败。
每项操作是否受固件支持，以 ACK 和回读结果为准。未回复或被拒绝的请求不能视为
已确认保存。

## 传输与请求匹配

使用设备配置的凭据，通过 TCP 1883 连接割草机的 MQTT Broker。
**先订阅** `data_point/122/robot`，再向 `data_point/122/app` 发送命令。
请求与回复均采用 protobuf JSON，字段使用下文的 snake_case 名称。
DP119 不是预约回复主题。

每次请求都使用不同的正有符号 int32 `seq`（1–2147483647），验证 GET 也不例外。
回复必须同时匹配 `seq` 和 `cmd_type`。忽略 retained 回复和其他请求的回复。
MQTT 发布成功或 PUBACK 只确认消息传输；`ScheduleAck` 确认设备处理结果，两者均不能
替代回读验证。

Protobuf 可能省略值为零的标量。ACK 省略 `cmd_type` 表示 GET；省略 `code` 表示
0（成功）。省略布尔值表示 false；省略 `items`、`disabled_week_days` 等重复字段
表示空列表。但成功的 GET 仍必须包含 `schedule_list` 对象，不能将格式损坏的数据
解释为空的成功结果。比较预约内容前，集成会规范化省略的默认值和星期排列顺序。

| 操作 | `cmd_type` | 数值 | 参数 |
| --- | --- | --- | --- |
| 读取 | `SCHEDULE_CMD_TYPE_GET` | 0 | 无 |
| 新增 | `SCHEDULE_CMD_TYPE_ADD` | 1 | `add_param` |
| 删除 | `SCHEDULE_CMD_TYPE_DELETE` | 2 | `delete_param.id` |
| 修改 | `SCHEDULE_CMD_TYPE_MODIFY` | 3 | `modify_param` |

`UPDATE` 和 `SAVE` 不是命令名称。ADD 和 MODIFY 参数包含 `schedule_type` 及对应的
`global_schedule_v2` 对象，不使用 GET 的 `schedule_list` 包装结构。
MODIFY 发送完整的替换参数，并附上已有 ID；DELETE 只发送 ID。

## 可编辑字段

| `global_schedule_v2` 内的路径 | 类型与约束 |
| --- | --- |
| `basic_config.week_days` | 非空星期列表：`WEEK_DAY_MONDAY` … `WEEK_DAY_SUNDAY`（ISO 数值 1…7），按集合处理。 |
| `basic_config.start_time.hour` | 整数 0…23 |
| `basic_config.start_time.minute` | 整数 0…59 |
| `basic_config.end_time.hour` | 整数 0…23 |
| `basic_config.end_time.minute` | 整数 0…59 |
| `basic_config.disabled` | 布尔值；禁用该条预约 |
| `basic_config.run_once` | 布尔值，预约模块 v3+；仅执行一次。条目被禁用不能证明已经执行完成。v2 应省略此字段。 |
| `repeat_until_end_time` | 布尔值，预约模块 v4+；在时间窗口内重复割草。更早的固件应省略此字段。 |

日历要求开始和结束处于同一个本地日期，结束晚于开始，且精确到整分钟。
单日全天事件映射为 00:00–23:59；跨夜和零时长的定时事件会被拒绝。
这些限制定义了日历支持的子集，并不表示固件具有额外容量或验证保证。
固件可能因时间冲突、容量限制或其他业务约束返回非零错误码。

协议时间是本地时钟时间，不含日期和时区。**请将 Home Assistant 和割草机设置为
同一时区。** 每周事件在夏令时切换后保持本地时钟时间。日历会跳过春季时钟前拨时
不存在的时间窗口；秋季时钟回拨时只展示重复时间窗口的第一次出现。
固件实际的夏令时执行行为仍需针对目标设备验证。创建或编辑指向第二次重复时段的
事件会被拒绝。

## 完整请求与回复示例

以下请求全部发布到 `data_point/122/app`，ACK 全部从 `data_point/122/robot`
接收。示例 ID 和序号仅用于说明；实际分配的 ID 应按下文的验证流程取得。

### 读取

请求：

```json
{"cmd_type":"SCHEDULE_CMD_TYPE_GET","seq":1001}
```

成功返回空列表（日出、日落字段也可能同时存在）：

```json
{
  "cmd_type":"SCHEDULE_CMD_TYPE_GET",
  "seq":1001,
  "code":0,
  "schedule_list":{
    "items":[],
    "global_disabled":false,
    "disabled_week_days":[],
    "schedule_mode":"SCHEDULE_MODE_TIME_SLOT"
  }
}
```

### 新增

每周三、周五 09:00–10:00 的预约（v4+ 示例）：

```json
{
  "cmd_type":"SCHEDULE_CMD_TYPE_ADD",
  "seq":1002,
  "add_param":{
    "schedule_type":"SCHEDULE_TYPE_GLOBAL_V2",
    "global_schedule_v2":{
      "basic_config":{
        "week_days":["WEEK_DAY_WEDNESDAY","WEEK_DAY_FRIDAY"],
        "start_time":{"hour":9,"minute":0},
        "end_time":{"hour":10,"minute":0},
        "disabled":false,
        "run_once":false
      },
      "repeat_until_end_time":false
    }
  }
}
```

设备处理成功的 ACK，**不包含已分配的预约 ID**：

```json
{"cmd_type":"SCHEDULE_CMD_TYPE_ADD","seq":1002,"code":0}
```

验证请求：

```json
{"cmd_type":"SCHEDULE_CMD_TYPE_GET","seq":1003}
```

回读示例，确认新 ID 为 7：

```json
{
  "cmd_type":"SCHEDULE_CMD_TYPE_GET",
  "seq":1003,
  "code":0,
  "schedule_list":{
    "items":[{
      "id":7,
      "schedule_type":"SCHEDULE_TYPE_GLOBAL_V2",
      "global_schedule_v2":{
        "basic_config":{
          "week_days":["WEEK_DAY_WEDNESDAY","WEEK_DAY_FRIDAY"],
          "start_time":{"hour":9,"minute":0},
          "end_time":{"hour":10,"minute":0},
          "disabled":false,
          "run_once":false
        },
        "repeat_until_end_time":false
      }
    }],
    "global_disabled":false,
    "disabled_week_days":[],
    "schedule_mode":"SCHEDULE_MODE_TIME_SLOT"
  }
}
```

### 修改

将 ID 7 的结束时间改为 11:00，并保留其余设置：

```json
{
  "cmd_type":"SCHEDULE_CMD_TYPE_MODIFY",
  "seq":1004,
  "modify_param":{
    "id":7,
    "schedule_type":"SCHEDULE_TYPE_GLOBAL_V2",
    "global_schedule_v2":{
      "basic_config":{
        "week_days":["WEEK_DAY_WEDNESDAY","WEEK_DAY_FRIDAY"],
        "start_time":{"hour":9,"minute":0},
        "end_time":{"hour":11,"minute":0},
        "disabled":false,
        "run_once":false
      },
      "repeat_until_end_time":false
    }
  }
}
```

```json
{"cmd_type":"SCHEDULE_CMD_TYPE_MODIFY","seq":1004,"code":0}
```

随后使用新序号 GET，检查 **ID 7** 的星期、时间及布尔设置是否与预期完全一致。
保留编辑前参数中的未知字段；集成也会保留禁用和重复割草至结束时间的设置。

### 删除

```json
{"cmd_type":"SCHEDULE_CMD_TYPE_DELETE","seq":1006,"delete_param":{"id":7}}
```

```json
{"cmd_type":"SCHEDULE_CMD_TYPE_DELETE","seq":1006,"code":0}
```

随后使用新序号 GET，确认列表中不再存在 ID 7。

### 失败

```json
{"cmd_type":"SCHEDULE_CMD_TYPE_MODIFY","seq":1004,"code":-1}
```

任何非零 `code` 都表示失败；不要擅自为 `-1` 指定协议未定义的详细含义。
缺失、格式损坏或不匹配的回复均不能确认编辑已保存。即使收到匹配的成功 ACK，
仍必须通过验证 GET 确认预期状态。本日历只发送已知且经过校验的命令，
每次编辑都要求回读。

## 事务与 ID 规则

每次编辑时，集成持有与预约开关共用的锁，并执行：

1. 重新 GET 取得基线，保留所有条目的 ID 和类型。
2. 使用新序号发送 ADD/MODIFY/DELETE，等待最多五秒，取得匹配且处理成功的 ACK。
3. 使用另一个新序号 GET，等待最多五秒，取得匹配的成功回复。
   发布有效快照，并在快照发生变化时通知 HA 日历监听器。
4. ADD：必须恰好新增一个 ID，且 GLOBAL_V2 内容匹配；MODIFY：ID、类型必须不变，
   内容必须匹配；DELETE：目标 ID 必须不存在。
5. 只有通过第 4 步才能报告编辑成功。有效回读即使与编辑请求不一致，仍作为设备实际
   状态展示，同时报告编辑失败。无法唯一确认 ADD 结果时也遵循该规则。

协议没有设备事务令牌、幂等键、ADD ACK 中的分配 ID、修订号或比较并交换机制。
并发 ADD 导致结果不明确时（例如出现多个新 ID），集成会拒绝确认，而不会猜测。
其他客户端同时编辑仍可能与回读竞争，因此应避免并发编辑。
设备可能已写入成功，但 ACK 或回读丢失：此时报告失败，并保留最后一次成功读取的
快照。读取或编辑失败不会清空日历缓存，也不会仅因失败就将其标记为不可用。
保留的快照可能过时，不能证明失败或超时的编辑已经应用；重试前请先刷新。
格式损坏的条目列表不能替换最后的有效快照。首次有效快照尚未取得，或断线、重置后，
日历会保持不可用，直到读到新的有效数据。切勿盲目重试 ADD 或自动执行破坏性回滚。
集成不会自行创造设备数据结构或新错误码。

ID 是设备分配的有符号 int32 标识符（日历接受包括 0 在内的非负 ID），不是列表
下标。HA 事件系列 UID 为 `global-<id>`，仅在对应割草机的日历内有效；日历的唯一
标识使用稳定设备 ID。
每周事件共用 UID 和 RRULE，但有意不设置 `recurrence_id`：每个显示的事件都代表
可编辑的完整设备规则。HA 前端的单次事件对话框没有整系列选择项，因此编辑或删除
任一事件都会影响整条设备预约，包括所有配置的星期和后续事件。
仅支持整系列修改和删除：`recurrence_id` 和 `recurrence_range` 必须不设置或为空
（前端会发送空值）。明确请求修改单次事件或“本次及以后”的操作会失败，且不会写入
设备。升级后请刷新日历，丢弃带有旧单次事件 ID 的条目。

## 日历编辑约定

使用 HA 日历界面或标准日历 WebSocket API。标题、位置和描述保存在 HA 本地，
关联稳定的割草机标识与整数设备条目 ID。这些字段**绝不会通过 DP122 发送**。
集成不会自动生成事件描述。HA 原生日历编辑器保持原样；不受支持的选项由 Python
校验逻辑在保存时报告。

| HA 字段 | 设备映射与支持行为 |
| --- | --- |
| 定时开始／结束 | 同一天内的本地整分钟 `start_time`／`end_time`，加星期；不发送日期 |
| 单日全天 | 设备 00:00–23:59；界面中开始、结束选择同一天；API 结束日期不包含在内（例如 11 月 18 日 → 11 月 19 日） |
| 多日全天 | 拒绝；只能选择一个本地日历日 |
| 不重复 | `run_once=true`，且只有一个星期 |
| 每天，间隔 1 | 全部七个星期，`run_once=false` |
| 每周，间隔 1，选择星期 | `run_once=false` 和 `week_days` |
| 每月／每年，或间隔不为 1 | 拒绝 |
| 重复结束：永不 | 无结束日期的每日／每周规则；设备没有结束日期字段 |
| 重复结束：某日期／若干次后 | `UNTIL`／`COUNT`，拒绝 |
| 标题／位置／描述 | HA 本地元数据，不是设备配置 |

全天表示配置的执行窗口，不保证持续割草。设备时间窗口有意不包含当天最后一分钟，
HA 仍显示为完整的一天。用户选择开始日期时，集成无法自动修改原生编辑器的结束
日期。单日事件应在该编辑器中将两个日期设为同一天。前端提交时会给显示的结束日期
加一天，打开全天事件时会减一天。因此在界面选择 11 月 18 日至 11 月 19 日表示
两天（API 为 11 月 18 日至 11 月 20 日），会被拒绝。

例如，每天、间隔 3 表示每三天一次，不是执行三次；未设置重复结束时会无限继续。
其规则为 `FREQ=DAILY;INTERVAL=3`，不受支持。设备频率预约是另一种模式，不在本
日历范围内。`repeat_until_end_time` 表示在单个作业窗口内重复割草，不是 HA 的
重复结束设置；修改预约时会保留该字段。

支持 `FREQ=DAILY` 或 `FREQ=WEEKLY`，可选 `INTERVAL=1`；每周规则可用不带序号的
`BYDAY=MO,TU,WE,TH,FR,SA,SU` 子集，且必须包含开始日期所在的星期。
间隔为 1 时，`WKST` 不影响结果。每日规则的 BYDAY 筛选、COUNT、UNTIL、其他频率
及重复例外均不支持。
新建重复事件必须选择下一个匹配窗口，也可以选择已开始但尚未结束的窗口
（`start <= now < end`）。例如，周三 20:00 可以保存周三 18:00–21:00 的每周事件。
保存已开始的窗口只更新预约配置；集成不会发送立即割草命令。每日规则遵循同一策略。
当天的单日全天重复事件，只要设备窗口（00:00–23:59）尚未结束，也可创建。
创建时会拒绝已结束的窗口，以及晚于下一个匹配窗口的 DTSTART：设备不保存开始日期，
无法据此推迟启用。

修改重复预约会变更整条设备规则，正在割草时也一样。集成只发送预约编辑与验证请求，
不会发送停止、重启或重新安排当前任务的命令。后续启动取决于保存的规则和设备条件，
选择的日历日期不能推迟设备规则生效。更新时省略重复规则，会保留当前重复规则及
每日／每周的显示选择。

没有重复规则时，日历通过 `run_once` 请求**仅执行下一次**。
只能选择指定星期和时间的下一次出现，不能指定任意未来日期。
一次性事件的开始时间必须严格晚于当前时间，即使结束时间尚未到，已开始的窗口也会
被拒绝，并返回：
`A one-time event must start in the future; choose a future start time`。
HA 通过该限制避免把已经过去的开始时间显示为未来的一次性执行。
因此，午夜后也不能创建当天的全天一次性事件。
创建或修改已启用的一次性设备窗口时，该条目、对应星期及全局预约开关必须全部启用，
避免所选日期被静默推迟。

一旦单个条目同时上报 `run_once=true` 和 `disabled=true`，HA 只允许编辑标题、
描述和位置。其时间、已记录日期、星期、重复规则及全天显示选择均被冻结，也不能
转换为每周／每日规则。保存不允许的修改时会返回：
`This one-time schedule is disabled; only its title, description and location
can be changed. Create a new event to schedule mowing again`。
不会发送 MODIFY，随附的文字修改也不会部分保存。允许的纯文字编辑会重新 GET，
保留已记录日期和禁用标志，仅保存 HA 元数据。仍可删除，但必须经过正常 ACK 和 GET
验证。需要再次预约时请创建新事件；日历不会自动重新启用旧条目。

此限制依据单个条目的标志，而非总开关或禁用星期列表，也不会冻结重复规则。
只要两个条目标志同时符合条件，限制即生效，任务正在运行时也不例外。
禁用不能证明已完成，甚至不能证明曾执行。HA 原生表单仍显示常规控件，由 Python
在保存时校验这些限制；表单没有新增单条预约的启用／禁用按钮。

允许保存已开始的重复窗口，并不放宽设备写入验证：每次 ADD/MODIFY/DELETE 都必须
取得匹配的成功 ACK，并通过 GET 确认预期结果。确认保存只描述配置已存储，
不代表割草已成功启动或会立即启动。

### 本地元数据与回退行为

设备编辑完成后，只有收到匹配的成功 ACK 并通过匹配的 GET 验证，才提交新的本地
元数据。仅本地编辑（文字，或设备配置相同的显示选择）会在同一预约锁内重新 GET
基线，再保存本地元数据，不发送 MODIFY。报告持久化成功前还会回读本地存储。
若持久化失败，HA 会报告错误并保留已确认的设备状态；再次写入前请刷新，尤其是 ADD。
读取失败和设备写入失败不会提交请求中的元数据。

HA 会跨 GET 和重启记住全天及每日／每周的显示选择。设备配置始终为准：
时间窗口改为非 00:00–23:59 时，移除全天显示提示；每日预约改为不含全部七个星期，
或改为一次性预约时，移除每日显示提示。本地文字继续关联同一个 ID。
有效时间段 GET 确认条目已删除或已改为其他预约类型时，移除该 ID 的元数据。

设备 ID 可以复用，并非 UUID 或时间戳，也不保证一直递增。HA 不会尝试识别离线期间
错过的删除／复用周期。只要同一 ID 仍然存在，本地文字就可能继续关联，设备字段则
跟随 GET。协议没有额外的身份标识。

本地元数据缺失时，重复事件仍按设备实际时间，在查询日期范围内的所有上报星期显示。
回退标题为 **Global mowing**，位置和描述为空，显示为定时事件和每周 RRULE，
即使设备时间为 00:00–23:59 或包含全部七个星期也是如此。设备数据无法证明用户
原先选择过全天或每日显示。一次性日期的回退受到下文限制。

对于每个一次性条目，HA 在有效 GET 中首次看到其已启用且具备执行条件时，记录下一
个符合条件的计划窗口，并考虑按星期禁用的设置。窗口过期或设备禁用该条目后，
记录的日期不变；查询过去的日历范围仍返回原事件。全局／按星期暂停不会擦除已知
日期，未变化的过期条目也不会滚动到下周。这是计划窗口，不是已执行割草的证明：
其他协议客户端发送的禁用，与设备自动禁用一次性条目，无法区分。

日期和本地元数据通过 HA 的 `Store` 辅助类一起持久化到
`.storage/terramow.schedule_history.<hashed-stable-device-id>`，跨重连、集成重新
加载和正常 HA 重启保留。新增的元数据部分兼容已有的仅日期存储。
备份时请包含 HA 配置目录及其中的 `.storage`。用相同配置重建容器仍能保留这些字段；
未恢复备份的新 HA 实例／配置无法从割草机恢复本地文字或显示选择。
仅有存储的历史记录不会使日历可用：连接后仍需新的有效 DP122 GET。
读取或编辑失败会保留最后的有效历史。写入仍要求设备 ACK 和 GET 验证；
发送命令本身不会创建已确认的日历记录。

设备存储星期和时间，不保存带日期的执行历史。首次发现条目时若它已禁用，且之前
没有记录日期，就无法将其放到某个历史日期；它会保留在 DP122 快照中，但不显示为
日历事件。本功能无法补填更早的执行日期。初始处于暂停状态的条目，也要等到首次
观察到符合执行条件时才会记录日期。HA 离线期间若错过完整的禁用／重新启用周期或
ID 复用周期，仅凭相同的 GET 无法识别。

观察到条目重新启用或时间／规则变化后，会将其已存的计划窗口替换为下一个符合条件
的窗口。转换为每周预约，或从有效设备列表中移除时，会删除对应的本地一次性记录。
因此，删除历史事件仍会通过 DP122 删除设备条目，并进行 GET 验证。
移除集成会删除其本地元数据／日期存储。这是当前仍存储的一次性预约的历史，
不是不可修改的执行日志。

每周配置的窗口即使禁用也会显示。日历 `on` 只表示当前处于配置的窗口内，
不表示割草机正在割草，也不保证在禁用、天气或业务条件限制下执行。
实际执行情况请看已有的割草机／任务实体，预约启用或禁用请使用已有开关。
日历不会自动切换全局或按星期开关。

标准 `calendar.create_event` 动作可以通过 `summary`、`start_date_time` 和
`end_date_time` 创建一次性事件。HA 动作参数结构没有 RRULE 字段；创建重复事件请
使用日历界面／WebSocket API。新增日历平台后请重启 HA，或在新代码已载入 HA
进程后重新加载集成。
